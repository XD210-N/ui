## 三、模拟的核心原则：走甲方原接口，只换数据来源

**这是我方模拟策略的灵魂，务必理解：**

模拟**不是**另写一套假前端，而是：
- 前端构造请求、解析返回的代码 = **甲方原代码，一字未动**。
- 模拟**只在"数据来源"上动手**——在 `app/api/` 下按**甲方前端期望的格式**返回假数据。
- 请求走的 URL、方法、body、返回字段，**全部严格对齐甲方前端既定契约**。

所以每个 mock 路由本质上是**一份"参考后端实现"**：它演示了"甲方前端期望真后端在这个端点返回长这样的数据"。

> 写 mock 时若发现要"猜"返回格式，先去甲方原前端代码里找解析逻辑（如 `MyRuntimeProvider` 的 SSE 解析、`ArtifactCanvas` 的 `data.supported`/`data.connected`），按它读取的字段反推格式，**不要自创格式**。

## 四、模拟的真正目的：自证清白 + 给甲方当排错参照

我方做模拟有两个目的，都不是"假装功能做完了"：

1. **自证清白**：我方本地没有甲方后端，无法跑真实链路。用模拟证明——**甲方这套前端接口代码 + 数据契约本身是能用的**。甲方覆盖后若接不上，可据此说明：「我的模拟用的就是你工程里这套接口，只把后端返回的数据换成了假的；接口代码我一字没改。所以接不上不是前端接口问题，而是真后端返回格式或环境配置对不上。」

2. **给甲方当排错参照**：甲方团队庞大、非一人负责，可能交接没对齐导致接口理解有偏差。我方的 mock 路由 + `甲方对接与模拟说明.md` 就是一份**可运行的"标准答案"**——甲方拿真后端返回去比对 mock，差异处即问题所在。

**必须诚实的边界**（这反而加强上面的论证）：
- 模拟能证明：**请求构造 + 返回解析（接口代码）是对的**。
- 模拟不能证明：**地址/路由配置在甲方环境下是通的**（模拟走本地，真实走甲方 `SAAS_URL`，"去哪"不同但"长什么样"相同）。
- 因此「mock 通、真实不通」恰好把责任锁定在**非我方前端接口代码**的两处：① 甲方真后端返回格式与契约不符；② 甲方环境地址配置（`NEXT_PUBLIC_SAAS_URL` / `next.config.ts` rewrite）没接对。

## 六、真实 / 模拟切换：用甲方原机制，不另造地址输入

- **真实模式**：完全用甲方原代码的地址机制——`const SAAS_URL = process.env.NEXT_PUBLIC_SAAS_URL ?? "http://localhost:8000"`。甲方内部本就知道这个环境变量，**不要再加"前端填后端地址"的输入框**，否则甲方会困惑「不是给你工程了吗，按里面接口来啊」。
- **模拟模式**：仅在前端把请求改道到本地 mock，作参照用。
- 切换不得改动甲方的 `MyRuntimeProvider` / `ProjectContext` 对接逻辑。

> ✅ 已查证（今早 404 根因，确定性结论）：甲方原工程**项目请求**（`ProjectContext.tsx` 的 `/v1/projects`）用**相对路径**，被 `next.config.ts` 自带 rewrite（`/v1/* → /api/v1/*`，destination 是本地相对路径不带 http）**固定转去前端自带 mock，永远到不了真后端**；而**线程/langgraph**（`MyRuntimeProvider.tsx`）用 `${SAAS_URL}` **绝对地址**打到真后端。甲方设好 SAAS_URL 后：项目走自带 mock 拿到 mock 项目 id → 线程/langgraph 带这个 id 打真后端 → 真后端没有此 id → 404 `Conversation not found`。**这是甲方原工程既有配置矛盾，非我方引入**（`ProjectContext.tsx`/`next.config.ts`/`MyRuntimeProvider.tsx` 与甲方逐字节一致）。本地不报错是因为本地 SAAS_URL 也置空、三类请求全落本地 mock 自洽。
> 修复（甲方二选一）：A. 把 `ProjectContext.tsx` 的项目请求改为 `${SAAS_URL}/v1/projects`（或把 rewrite destination 指向真后端）；B. 调整 rewrite/后端路由对齐。已写入给甲方的 `甲方对接与模拟说明.md` 头号排查项。
